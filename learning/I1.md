# Stage I1: The identity primitives

*Expanded from `learning/Learning-Track.md`. The stage is done when the checkpoint passes out loud, cold. Everything below exists to get you there. This is the foundation the whole identity lane stands on, so it is longer than most stages. Go slowly.*

---

## The checkpoint, and what passing sounds like

Say all five, cold.

1. **Draw authorization-code-plus-PKCE with every hop labeled.** The app creates a random verifier and hashes it into a challenge. It sends the user's browser to the authorization server with the challenge, a client ID, a redirect URI, and scopes. The user authenticates and consents. The server redirects back with a short-lived authorization code. The app exchanges the code plus the original verifier for tokens at the token endpoint. The verifier proves that whoever got the code is the same party that started the flow, which is what makes the code useless to anyone who intercepts it.
2. **ID token vs. access token.** An ID token (OIDC) is a JWT *for the app* that says who the user is and how they authenticated. An access token (OAuth) is *for the API* and says what the bearer may do. Apps that read an access token to identify a user, or send an ID token to an API, have confused authentication with authorization. That confusion is a real bug class.
3. **Define a scope, and name two things a scope cannot protect you from.** A scope is a label on a token that bounds what the token may be used for at the API. It does not protect you from a stolen token (the thief has the same scope), it does not limit *how long* the token works (that is lifetime), and it does not tell you *who* is using it (that is attribution). Scope is necessary and nowhere near sufficient.
4. **Why a long-lived static API token is the same problem as a shared password.** It does not expire, it is not bound to a session or device, it is copied into config files and repos, anyone holding it is indistinguishable from the owner, and rotating it breaks things so nobody does. Everything wrong with passwords, minus the human who might notice.
5. **Token exchange in one sentence, and the case it exists for.** RFC 8693 lets a party trade one token for another with a different audience or narrower scope, optionally recording *who is acting for whom*. It exists for delegation: a service, or an agent, acting on a user's behalf downstream without carrying the user's full credential. Send an actor token and you get delegation with an audit trail; omit it and you get impersonation.

---

## Why this stage matters for a SOC analyst

Okta's System Log, CloudTrail's assumed-role sessions, a consent-phishing alert, and every agent-identity design you will ever evaluate are these five ideas wearing product names. If you can draw the PKCE flow and explain what a scope does not protect, the admin console at work stops being magic and the identity attacks in I5 become obvious.

## The path, in order

### 1. The one-hour overview. (Nate Barbettini, 62 minutes, shift time)
**OAuth 2.0 and OpenID Connect (in plain English)**, YouTube, from Okta's developer team. Slides at speakerdeck.com/nbarbettini. Start here even if you think you know OAuth. He explains the problem OAuth solves, the flows, scopes, tokens, and why OIDC was bolted on top.
**Extract:** the difference between authentication and authorization, which is checkpoint item 2 in embryo. Write down the four roles (resource owner, client, authorization server, resource server) and say what each one holds.

### 2. The free book, selected chapters. (Aaron Parecki, OAuth 2.0 Simplified, free at oauth.com, about 3 hours total, shift time)
Read in this order: **Background** · **Authorization** (the authorization code flow) · **Scope and Redirect URLs** · **Access Tokens** · **Protecting Apps with PKCE** · **Client Credentials** (under the grant types; this is how machines and agents get tokens, and it matters for I6) · **OpenID Connect**.
Skip the server-building chapters; you are learning to read flows, not to build a server.
**Extract:** checkpoint items 1, 2, and 3. After the PKCE chapter, draw the flow on paper without looking. After the Scope chapter, write the two things scope cannot protect you from.

### 3. What OAuth 2.1 changed and why. (30 minutes, shift time)
oauth.net/2.1 and connect2id.com/learn/oauth-2-1. OAuth 2.1 is still an IETF draft (draft-ietf-oauth-v2-1-15, March 2026) but every major provider already treats it as the baseline.
**Extract:** the implicit flow is gone, PKCE is required for every client, bearer tokens never go in a URL query string, and refresh tokens for public clients must be sender-constrained or rotated. Each of those is a lesson learned from a real attack. Say what attack each one closes.

### 4. JWTs, by breaking them. (PortSwigger Web Security Academy, JWT attacks, free, browser, 2 to 3 hours across shifts)
portswigger.net/web-security/jwt. Read the topic page, then do the labs in order: **authentication bypass via unverified signature** · **via flawed signature verification** (the `alg: none` trick) · **via weak signing key** · **via algorithm confusion**. Use jwt.io to decode tokens as you go, never a real token from anywhere.
**Extract:** JWT anatomy (header, claims, signature) and "the alg pitfalls" for real. The lesson under the labs: a JWT is only as trustworthy as the verifier's discipline. This is also the first hands-on identity attack you have run, which makes it case-file material if you want it.

### 5. OAuth, by breaking it. (PortSwigger, OAuth authentication labs, free, browser, 2 to 3 hours across shifts)
portswigger.net/web-security/oauth. Read the topic page, then the labs. They cover implicit-flow misuse, missing state (CSRF), redirect URI flaws that leak the authorization code, and scope upgrade.
**Extract:** why each OAuth 2.1 rule from step 3 exists. When a lab leaks a code through a bad redirect URI, that is the attack PKCE was designed to survive. Connect each lab to a line in the spec.

### 6. SAML, enough to read a breach. (1 hour, shift time)
WorkOS, **The developer's guide to SAML authentication** (workos.com/blog), then one **signature wrapping** explainer (security.unboundcompute.com/saml-signature-wrapping). SAML still runs a large share of enterprise SSO, including what you see at work.
**Extract:** the assertion flow (IdP builds a signed assertion, browser posts it to the SP's ACS URL, SP validates signature, audience, and time). Then the classic failure: the SP validates *a* signature but reads a *different* assertion. Say why "the signature was valid" is not the same as "the assertion was valid."

### 7. SCIM, the boring one that leaves access behind. (45 minutes, shift time)
Clerk, **SCIM 2.0 explained** (clerk.com/articles), then Okta's **SCIM 2.0** developer page (developer.okta.com). RFC 7643 (schema) and RFC 7644 (protocol) are the reference, not the reading.
**Extract:** provisioning is create, update, deactivate over REST, driven by the IdP, authenticated by a bearer token. Then the security angle, which is the whole reason it is in this track: a SCIM token is a standing credential with write access to accounts, and a failed deprovisioning leaves access behind. Say where that shows up in I2's tenant inventory.

### 8. Token exchange, RFC 8693. (1.5 hours, shift time)
Read the **ZITADEL token exchange guide** (zitadel.com/docs/guides/integrate/token-exchange) first, for the delegation vs. impersonation picture. Then the RFC itself (rfc-editor.org/info/rfc8693), sections 1 through 2 and the `act` and `may_act` claims. Then the **MojoAuth worked example of token exchange for agent delegation** to see it applied to the I6 problem.
**Extract:** checkpoint item 5, exactly. The `sub` claim is who the token is about, the `act` claim is who is acting for them, `may_act` says who is allowed to. The actor token is the whole difference between a delegation with an audit trail and an impersonation with none. This is the primitive the agent lane will be built on.

### 9. SPIFFE, read only. (30 minutes, shift time)
spiffe.io: the **overview** and the **SPIFFE concepts** page. Do not deploy anything.
**Extract:** the three words: a **workload** gets a short-lived **SVID** (an identity document, X.509 or JWT) from a **trust domain**, via a local Workload API, with no secret to copy. That is what "identity for things that aren't people" looks like when done properly, and it is the counterexample to checkpoint item 4.

### 10. Hands-on, home time: run the flows yourself. (one evening)
Run Keycloak locally in Docker (this is also a preview of the lab IdP in I5). Create a realm, a user, and two clients: one public client for authorization-code-plus-PKCE, one confidential client for client credentials. Then:
- Do the PKCE flow in a browser and curl, and read every parameter in every redirect.
- Do the client-credentials flow with curl and decode the access token at jwt.io.
- Turn on Keycloak's token exchange and trade the user's token for a narrower one. Read the `act` claim.
**Extract:** every checkpoint item, felt rather than read. Fake users and fake credentials only.

### Reference, not reading
- **The Little Book of OAuth 2.0 RFCs** (Parecki, free PDF at oauth.net/books). The map of which RFC does what. Keep it open while reading the rest.
- **OAuth 2 in Action** (Richer and Sanso). Buy it only if the free book left you wanting the deep version.

## Self-test (say these cold)

- The five checkpoint items, in your own words, on paper for item 1.
- An app is granted scope `read:mail`. Its access token is stolen. What can the thief do, and what did the scope prevent?
- Why is an access token in a URL query string a problem? Name two places it ends up.
- What is the difference between a refresh token and a long-lived access token, and why does that difference matter for detection?
- A SAML response has a valid signature. Give one way it can still authenticate the wrong user.
- A service account's SCIM token leaks. What can an attacker do with it, and what log would show it?
- An agent needs to read a user's calendar on their behalf. Describe the token it should hold, what its `sub` and `act` claims say, and what it must not hold.
